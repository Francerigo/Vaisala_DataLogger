// 01 · Project Purpose

Why This Tool Was Built

The GMP343 DataLogger was designed for unattended, long-term CO₂ monitoring across multiple sensor nodes. The target environment is a dedicated Windows computer that boots automatically into a single administrator account and starts the application without any human interaction.

🏭

Unattended Deployment

The system is designed for set-and-forget installation. Once powered on, Windows auto-logs in and the application starts automatically, requiring no operator presence during normal operation.

📡

Multi-Sensor Polling

Polls any number of Vaisala GMP343 sensors on a shared RS-232 bus using Modbus-style addressing. Sensor addresses are configured at runtime via a simple comma-separated input field.

💾

Dual Storage Redundancy

Every reading is written to the local C: drive and, when available, simultaneously mirrored to an external USB drive on D: — ensuring data is never lost if one medium fails.

📶

Bluetooth Data Retrieval

A background RFCOMM server lets field personnel wirelessly retrieve the full log file from a mobile device without physical access to the machine or removing the USB drive.

🌡️

CO₂ + Temperature

Each sensor poll returns both CO₂ concentration (ppm) and temperature (°C) in a single response, which the parser extracts and stores in paired columns per sensor.

📊

Analysis-Ready CSV

Output files use a clean, auto-generated CSV schema with one timestamp column and paired co2/temp columns per sensor, ready for Excel, Python, or any data tool.

// 02 · System Architecture

How the System Is Structured

The application is a single Windows Forms executable running three concurrent threads: the main UI thread, a serial polling timer, and a Bluetooth listener loop. All sensor state is managed in-memory between timer ticks.

// 03 · How It Works

The Data Pipeline, Step by Step

From power-on to a saved CSV row, every stage of the pipeline is handled automatically. Here is a detailed walkthrough of what happens from the moment the application starts.

1. Auto-Start on Boot

The Windows machine is configured with a single administrator local account set to auto-logon. The application is registered to launch at startup (via the Startup folder or Task Scheduler), so no user action is needed after the PC is powered on. The form loads immediately.

2. Form_Load: Serial & Bluetooth Initialization

Form1_Load configures the SerialPort (COM3, 19200 baud, 8N1, carriage-return line terminator) and attaches the SerialPort_DataReceived event handler. Simultaneously, StartBluetoothServer() checks for an active Bluetooth radio and, if found, starts a BluetoothListener on the Serial Port Profile (SPP) UUID in a background thread. Logging then starts automatically by calling btnStartStop_Click programmatically.

3. Address Parsing & Buffer Allocation

The user-entered sensor addresses (e.g. 1,2,3,4) are split and trimmed into a List<string>. Parallel arrays — currentLineCO2[], currentLineTemp[], and sensorDataReceivedFlags[] — are allocated with one slot per sensor. These in-memory buffers accumulate readings until a complete row is ready to write.

4. Log File Initialization

InitializeLogFiles() creates C:\CO2_DataLogs\ if it does not exist, then writes the CSV header row (e.g. timestamp,co2_s1,temp_s1,co2_s2,temp_s2,…) only if the file is new — existing logs are never overwritten, only appended.

5. Timer-Driven Polling Loop

A Windows.Forms.Timer fires every N × 1000 milliseconds (where N is the user-configured interval in seconds, default 150 s). On each tick, logTimer_Tick discards stale serial buffer data and sends a SEND <address>\r command to the sensor at the current index, then advances the index round-robin. Each sensor is polled one at a time.

6. Serial Response & Parsing

When the GMP343 sensor responds, SerialPort_DataReceived fires on a background thread, reads one line, strips any Vaisala prompt characters (>), then marshals onto the UI thread via Invoke. ParseAndStoreData() splits the response on dash (-) delimiters — the GMP343 format is CO2 ppm - RH % - Temp °C — extracts tokens at index 0 and 2, and stores them in the correct buffer slot using the preceding sensor index.

7. Row Completion & CSV Write

After each parse, IsRowComplete() checks whether all sensor flags are set. When every sensor in the current cycle has reported, ParseAndStoreData() assembles a comma-separated CSV line with the current timestamp and all CO₂/temperature pairs, appends it to the local file, and — if drive D: is mounted — appends to the external file too. Buffers are then reset via ResetRowBuffers() for the next cycle.

8. Bluetooth Data Serving

In parallel, the BluetoothListenLoop thread waits for incoming RFCOMM connections. When a client connects (e.g. a phone with a Bluetooth terminal app), HandleClientSession reads commands: sending LOG returns the full contents of the local CSV file over the Bluetooth stream; sending EXIT cleanly disconnects. Multiple clients can connect sequentially without restarting the server.

// 04 · Data Format

CSV Output Schema

Both log files share an identical schema. The header is generated dynamically at startup based on the number of configured sensors. All values use standard ASCII with no quoting required.

timestamp

Local system time at the moment the complete row is written. Format: yyyy-MM-dd HH:mm:ss.

co2_sN

CO₂ concentration in ppm from sensor at address N. Raw numeric string as returned by the GMP343.

temp_sN

Temperature in °C from sensor at address N. Taken from the third dash-delimited segment of the GMP343 response.

NaN placeholder

If a sensor fails to respond before the row is committed, its CO₂ and temperature fields are filled with NaN to preserve CSV alignment.

// 05 · Setup & Deployment

Getting It Running

Full deployment from hardware wiring to automatic startup. All steps apply to a fresh Windows 10/11 machine configured as a dedicated logging station.

01

Hardware Prerequisites

Connect GMP343 sensors to the PC via RS-232 (or USB-to-RS232 adapter). Ensure the sensors are configured to Vaisala serial communication mode (19200 baud, 8 data bits, no parity, 1 stop bit). Assign each sensor a unique address. Note which COM port the adapter appears as in Device Manager.

02

Serial Port Configuration

In Form1.cs, the port is hardcoded to COM3. If your adapter appears on a different port, update serialPort.PortName = "COM3"; to match before building. All other serial parameters (19200 baud, 8N1) match Vaisala defaults and should not need changing.

03

Build the Application

Open GMP343_DataLogger.csproj in Visual Studio 2019 or later. Restore the NuGet package (32feet.NET v3.5.0.0) via Tools → NuGet Package Manager → Restore. Build in Release mode. The output .exe will be in bin\Release\.

04

Configure Windows Auto-Logon

Open netplwiz (Run → netplwiz). Select the local administrator account, uncheck "Users must enter a user name and password", click OK, and enter the account password when prompted. Windows will log in automatically on every boot.

05

Register Application for Auto-Start

Place a shortcut to GMP343_DataLogger.exe in C:\Users\<account>\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup. Alternatively, create a Task Scheduler task that triggers on user logon and runs the executable. The application calls btnStartStop_Click automatically from Form1_Load, so logging begins with no further user action.

06

Configure Sensor Addresses & Interval

The UI shows two settings: Sensor Addresses (comma-separated, e.g. 1,2,3,4) and Log Time Interval (s) (default 150 s). The total cycle time equals interval × number of sensors. These values are read from the UI text fields each time logging starts, so they can be changed before the next start without rebuilding.

07

External USB Drive (Optional)

Insert a USB drive. If Windows assigns it drive letter D:, the application will automatically detect it and mirror all log entries to D:\external_gmp_343_logs.csv. If the drive is absent or assigned a different letter, logging continues locally with a warning in the display. No configuration is required.

08

Bluetooth Data Retrieval

Pair a phone or laptop with the logging PC. Open a Bluetooth terminal app and connect to the device. Send the command LOG (uppercase) to receive the full CSV log contents. Send EXIT to close the connection cleanly. The server remains active continuously regardless of whether the application is currently logging.

// 06 · Development History

How the Project Was Built

The application was developed incrementally, with each layer of functionality added and tested before the next was started. Below is the chronological development story.

Design decisions

Windows Forms over WPF

Chosen for its simplicity and the fact that the UI surface is minimal — only a log display and two input fields. WPF's data-binding infrastructure would have added complexity without benefit.

Round-Robin Polling

Rather than issuing all sensor commands in a burst, the timer fires once per sensor with a configurable delay. This respects the GMP343's response latency on a shared bus and avoids collisions.

32feet.NET for Bluetooth

The 32feet.NET library was selected because it exposes a clean BluetoothListener API that mirrors TcpListener, making the server-side code easy to reason about. It supports RFCOMM SPP out of the box without WinRT.

In-Memory Row Buffers

CSV rows are only written when all sensor slots in the current cycle are filled (or a NaN is substituted on timeout). This prevents half-populated rows from corrupting the log and keeps every row aligned to the same timestamp.

// 07 · Known Limitations & Notes

Things to Be Aware Of

Practical notes for field deployment and future development.

COM Port is Hardcoded

The serial port is fixed to COM3 in code. If the USB-to-RS232 adapter enumerates on a different port, the source must be updated and rebuilt. A future improvement would expose this as a UI setting.

USB Drive Letter Fixed to D:

The external mirror path assumes D:\. If Windows assigns the USB drive a different letter, external logging silently skips with a warning. The local log is always written regardless.

Bluetooth LOG Sends Full File

The entire CSV file is transmitted on each LOG command. For very long deployments, this transfer can be large. A future version could support sending only the last N rows or a date range.

Single Bus / No MODBUS CRC

The polling uses Vaisala's text-mode SEND command rather than MODBUS RTU binary framing. This is simpler but relies on the sensor's text response format remaining consistent.

No Timestamp Per Sensor

The timestamp recorded in the CSV reflects the moment the last sensor in the cycle replies, not when each individual sensor was polled. For most monitoring use cases this is acceptable.

No Remote Configuration

Sensor addresses and interval must be set in the UI before logging starts. Changing them over Bluetooth is not currently supported. Only the LOG and EXIT commands are implemented.
